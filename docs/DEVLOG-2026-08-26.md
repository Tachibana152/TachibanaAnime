## ③ MySQL + Redis 数据库设计

**Q：帮忙设计一套 MySQL 数据库，还有 Redis 数据库。**

### 决策确认（3 个问题）

| 决策项 | 选择 |
|---|---|
| Redis 用途 | **完整三用途**：登录态 + 热点缓存 + 浏览量计数 |
| 种子数据 | **照搬前端 Mock**（6 用户/17 动漫/5 帖/6 回复，ID 对齐） |
| 外键策略 | **不用物理外键**（仅索引 + 应用层校验，利于逻辑删除） |

### MySQL 设计（库 `animeairi`，utf8mb4，InnoDB）

| 表 | 说明 | 关键索引 |
|---|---|---|
| `sys_user`（改） | 新增 `role`（USER/ADMIN/SUPER_ADMIN） | `uk_username` |
| `anime`（新） | 动漫信息（标题/日文名/分类/封面/制作阵容/简介/内容/浏览量/排序） | `idx_category`/`idx_sort`/`idx_title` |
| `forum_post`（新） | 帖子（状态 0待审/1发布/2驳回、置顶、浏览量、回复数冗余计数） | `idx_user_id`/`idx_status`/`idx_top_time` |
| `forum_reply`（新） | 回复 | `idx_post_id`/`idx_user_id` |

- 全部含 `deleted` 逻辑删除（`@TableLogic`）+ `create_time/update_time` 审计
- 种子数据与前端 Mock 完全一致（注意：Mock 实际是 **17** 部动漫，非 18）

### Redis 设计

沿用 `RedisConfig`（String key + JSON value），`RedisConstants` 扩展为三组：

| 用途 | Key 模式 | TTL | 说明 |
|---|---|---|---|
| 登录态 | `login:token:{userId}` | 7200s | 当前有效 token，登出/禁用/改密时删 → 强制下线 |
| 登录态 | `login:user:{userId}` | 3600s | 用户信息缓存，鉴权免查库 |
| 热点缓存 | `cache:anime:{id}` | 600s | 动漫详情，更新时 DEL |
| 热点缓存 | `cache:post:{id}` | 300s | 帖子详情 |
| 浏览量计数 | `count:anime:{id}` / `count:post:{id}` | — | INCR 累加，定期/读时合并回 MySQL |

### 认证方案讨论：JWT 与 Redis 如何配合

**Q：token 验证是 JWT 判断一致还是直接查 Redis？**

**结论：主验证 JWT，Redis 做补充（方案 A，双校验缺一不可）。**

| 校验 | 作用 | 漏掉后果 |
|---|---|---|
| ① JWT（`JwtUtil.parseToken`） | 验签名 + 过期，取 userId/role | 无法确认 token 真伪，Redis key 无从查 |
| ② Redis（`GET login:token:{userId}` 比对） | 确认会话仍有效 | 登出/禁用/顶号后旧 token 7200s 内仍可用 |

执行顺序：先 ① 后 ②。① 是身份校验（token 真假），② 是会话校验（token 是否仍有效）。可选降级开关 `security.redis-session.enabled=false` 退回纯 JWT。

**落地**：重写 `init.sql` + 扩展 `RedisConstants`（`CACHE_ANIME_PREFIX`/`CACHE_POST_PREFIX`/`COUNT_ANIME_PREFIX`/`COUNT_POST_PREFIX` 及 TTL）。

## ⑥ 后端认证实现与排坑

### 踩坑：循环依赖导致启动失败

```
APPLICATION FAILED TO START
The dependencies of some of the beans in the application context form a cycle:
authController → authServiceImpl
```

**原因**：`AuthServiceImpl` 中有 `@Resource private AuthServiceImpl authServiceImpl;` 自注入（误加的无用代码，全项目仅一处声明且从未使用），形成自环。Spring Boot 3 默认禁止循环引用。

**修复**：删除该自注入字段 + 无用的 `jakarta.annotation.Resource` import。

### 登录逻辑修复

- `selectById(username)`（按主键查，永远查不到）→ `selectCount(eq(username)) > 0` 正确查重
- `generateToken(..., SecurityConstants.ROLE_USER)` 硬编码 → `user.getRole()`，admin/超管 token 携带真实角色
- `UserVO` 缺 `role` 字段（与 `api.md` 契约"登录返回 user.role"不符）→ 补字段并在 `from()` 映射
- `SysUser` 实体缺 `role`（编译报找不到 `getRole`）→ 补字段，与库表一致

### 并发同名注册

**Q：并发注册重复用户名怎么解决？**

利用 `uk_username` 唯一索引：`selectCount` 预检查保留（常规友好提示），`insert` 包 `try/catch (DuplicateKeyException)` → 转 `BusinessException(400, "用户名已存在")`，兜住两个请求同时通过预检查的竞态窗口。

### 插入时间问题

用户指出"插入时间弄没了"：`MetaObjectHandlerConfig` 会自动填充审计字段，但按用户要求**恢复显式赋值** `setDeleted(0)/setCreateTime(now)/setUpdateTime(now)`（无冲突，自动填充只在字段为 null 时生效）。

### me() 接口实现

```java
public UserInfoVO me() {
    Long userId = UserContext.getUserId();          // 拦截器已写入
    if (userId == null) throw new BusinessException(401, "未登录");
    SysUser sysUser = sysUserMapper.selectById(userId);  // @TableLogic 自动过滤已删除
    if (sysUser == null) throw new BusinessException(401, "未登录");
    if (sysUser.getStatus() != null && sysUser.getStatus() == 0)
        throw new BusinessException(401, "账号已被禁用");
    // 字段映射 → UserInfoVO
}
```

- `/api/auth/me` 不在白名单 → `AuthInterceptor` 先校验 JWT 并写入 `UserContext`
- 返回的 `role` 取自数据库最新值（改角色后立即生效）
- 补禁用用户判断：登录后中途被禁用 → 401
